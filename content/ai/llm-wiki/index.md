## RAG가 채우지 못하는 부분

AI를 통해 정보를 얻을 때 주로 사용되는 방법은 RAG(Retrieval-Augmented Generation)이다. 원문을 청크로 나눠 벡터로 저장하고, 질의마다 유사 청크를 검색해 AI에 넘기는 구조다. 작동은 하지만 사용하다 보면 구조적 한계가 드러난다. 여러 문서에 걸친 관계 추론이 어렵고, 매 질의마다 **원문에서 다시 시작**한다. 

{{< linkcard url="https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f" title="LLM Wiki — Andrej Karpathy" description="Karpathy의 원본 아이디어와 커뮤니티 구현 사례들" site="GitHub Gist" >}}

Andrej Karpathy가 제안한 **LLM Wiki**는 이 방향을 뒤집는다. AI가 소스를 읽고 이해한 결과를 위키 형태로 누적한다. 다음 질의부터는 원문이 아닌 이미 정리된 위키를 읽는다. RAG처럼 매 요청마다 원문을 재검색하는 대신, **영구적인 누적 정보**를 쌓는 구조다. 특히 정보가 누적되기에 이전에 했던 질문을 다시 할 땐 AI를 통하지 않고 위키에서 직접 가져올 수 있다.

직접 써보면서 배운 건 이 구조가 자동화보다 **AI와 역할을 나누는 방법**을 익히는 과정이라는 점이다. 어떤 작업을 AI에게 맡길 수 있는지, 그걸 일관되게 만들려면 무엇을 명시해야 하는지가 핵심이다.

## 작동 원리

LLM Wiki는 세 계층으로 구성된다.

**Raw sources** — 원본 문서 모음이다. 아티클·논문·이미지·데이터 파일이 여기에 해당한다. 불변이며 AI는 읽기만 하고 **절대 수정하지 않는다**.

**Wiki** — AI가 소유하는 마크다운 파일 디렉터리다. 소스가 들어올 때마다 관련 페이지를 만들거나 갱신하고, 교차참조와 일관성을 유지한다. **사람은 읽고, AI가 쓴다.**

**schema** — AI에게 위키 구조·컨벤션·워크플로를 알려주는 설정 문서다. 도메인에 맞게 무엇이 효과적인지 파악하면서 사람과 AI가 함께 진화시킨다.  
Claude 기준으로는 기본적인 `CLAUDE.md` 파일 및 여러 스킬이 포함된다.

---

이 세 계층을 기반으로 사용자는 세 가지 방식으로 AI와 소통한다.

### Ingest — source를 wiki로 변환

source를 넣고 처리를 요청하면 해당 파일을 읽고 요약한 내용을 기반으로 새로운 노트를 만들거나 기존 노트를 갱신한다. 이 과정에서 파일 간의 교차참조와 위키링크가 자동으로 갱신된다.

### Query — 위키 기반 질의응답

질의가 들어오면 관련 페이지를 찾아 읽고 인용과 함께 답변한다. 가치 있는 답변(비교·분석·발견한 연결)은 새 노트로 위키에 다시 파일링된다. 탐색 자체가 위키를 풍부하게 만드는 과정이다.

### Lint — 정기 건강검진

주기적으로 위키 상태를 점검한다. 끊어진 링크, 서로 모순되는 주장, 낡은 내용, 누락된 교차참조를 찾아 수정을 제안한다.

**Claude Code**와 **Obsidian**을 조합해서 구현했다. 우선 Obsidian에서 새로운 Vault를 생성하고, 해당 루트 폴더를 대상으로 Claude Code를 실행한다. Karpathy의 `llm-wiki.md` 파일과 함께 아래 3단계 계획을 제공한다.

- **Phase 1** — 3계층 기반 구조
  - `raw/` 폴더에 원본 문서 보관. 이미지가 필요한 경우 `raw/assets/`에 보관
  - `notes/` 폴더에 위키 페이지 평평한 구조로 보관. `index.md` 파일로 콘탠츠 색인 및 사용자 정보(직무, 관심사 등) 저장. 모든 수정사항은 시간순으로 `log.md`에 기록
  - `CLAUDE.md`(3계층·핵심 원칙·폴더 규칙·노트 작성 규율) 파일 작성. `templates/note.md`로 생성될 note의 frontmatter 작성

- **Phase 2** — Ingest · Query · Lint 스킬 정의
  - `/ingest` — 소스 읽기 → 소스 노트 + 개념 노트 생성·갱신 → `index.md` 갱신. 노트 생성시 `index.md`의 사용자 정보 기반으로 개념 정리
  - `/query` — 근거 노트 탐색 → 인용 포함 답변 → 가치 있는 답변은 위키에 파일링
  - `/lint` — 끊어진 링크·고아 노트·모순·낡은 내용 점검 → 승인 후 수정

- **Phase 3** — 자동화 스크립트
  - 일관성 및 토큰 최적화 목적으로 제작
  - 스킬에서 반복 작업·포맷 처리 등 자동화 가능한 부분은 스크립트로 추출한다

스키마(`CLAUDE.md`)와 스킬의 큰 방향만 잡아주면 구조 설계와 스크립트 구현은 AI가 전담한다.

## 장점과 한계

**RAG와 비교한 장점**

토큰 수가 100,000 이하인 지식 베이스에서 LLM Wiki가 RAG를 앞서는 이유는 구조에 있다. RAG는 청크 단위로 검색하므로 관련 내용이 여러 청크에 흩어져 있으면 누락된다. LLM Wiki는 이미 교차참조된 위키를 읽으므로 연결이 보존된다. 벡터 DB, 임베딩 파이프라인, 검색 서버 없이 마크다운 파일만으로 작동한다는 점도 운영 부담을 줄인다.

유지보수 비용도 낮다. AI는 지루해하지 않는다. 교차참조 추가, 역방향 링크 갱신, 15개 파일을 한 번에 수정하는 작업을 사람이 하면 금방 포기한다. `CLAUDE.md`에 규칙을 명시해두면 AI가 일관되게 수행한다.

**한계**

환각 누적이 가장 큰 위험이다. 노트 하나에 환각이 들어갈 확률이 0이 아니면, 위키가 커질수록 어딘가에 잘못된 내용이 존재할 가능성은 1에 수렴한다. Lint로 주기적으로 검증하거나 중요한 노트를 직접 확인하는 과정이 필요하다.

규모 한계도 있다. 노트가 수백 개를 넘어가면 `index.md` 카탈로그만으로는 탐색이 어려워진다. 이 시점부터 BM25+벡터 하이브리드 검색 같은 도구가 필요하다. LLM Wiki는 RAG를 대체하는 게 아니라 소규모 지식 베이스에서 RAG 없이 시작할 수 있는 대안이다.

어휘 일관성 유지도 신경 써야 한다. AI가 같은 개념을 매번 다른 용어로 태깅하면 위키가 파편화된다. `CLAUDE.md`에 허용 태그 목록이나 용어 규칙을 명시하면 완화할 수 있다.
